# 架构说明：消息总线、进程边界与关闭顺序

## 为什么只有一个中央消息总线

QFramework 把模块发现、生命周期和消息传递分开。模块只声明主题并发布字节，不持有其他模块对象，也不直接建立 Socket、共享内存或 RPC 连接。

```text
QFrameworkApp.exe
├─ QFramework.dll
│  ├─ FrameworkConfig / Logger / MessageBus
│  ├─ PluginManager -> InProcessUi / InProcessNonUi DLL
│  ├─ ProcessSupervisor -> ProcessUi / ProcessNonUi EXE
│  └─ MainWindow / Dock / Layout / Style
└─ QFrameworkProtocols.dll
   └─ 所有 .proto 生成代码
```

中央路由带来三个直接结果：

1. 发布者只依赖主题，不依赖订阅者是否存在。
2. 每个订阅者有独立队列，一个慢模块不会直接阻塞其他模块。
3. 进程内与子进程模块看到相同的 `publish()` 和 `onMessage()` API。

框架不保存历史消息。发布时尚未加载或尚未订阅的模块不会补收。

## 依赖方向

依赖始终由下向上：

```text
QFrameworkProtocols.dll
          ↑
QFramework.dll
          ↑
QFrameworkApp.exe 与四类模块
```

`.pb.cc` 只在 `QFrameworkProtocols.dll` 编译一次，其他项目包含具体 `.pb.h` 并链接导入库。这避免多个 DLL 各自带一份 Protobuf 生成实现。

## 模块边界

主进程 DLL 使用 `QPluginLoader`，适合低开销 UI 或业务模块。框架可以捕获普通 C++ 异常，但 DLL 与主程序共享地址空间，严重内存错误仍可能终止整个应用。

子进程 EXE 使用 `QProcess`，适合需要故障隔离、独立模态窗口行为或单独调试的模块。进程崩溃不会直接破坏主进程地址空间，监督器可以重启它。

首版不做 ABI 版本协商、DLL 热卸载或热重载。更新主进程模块后必须重启框架。

模块启动采用“先开放发布入口，再执行回调”的顺序：

```text
注册主题 -> 开放当前模块 publish -> onStart()
                              ├─ true：保持发布权限并进入 Running
                              └─ false/异常：立即撤销发布权限并标记启动失败
```

因此模块可以在 `onStart()` 中发布初始化完成消息。发布入口开放不等于中央总线
已经开始向所有订阅者投递；框架仍会等待启动批次收口后再统一放开消费，避免其他
模块的生命周期回调与消息处理无序交错。

## 消息顺序与背压

每个模块拥有一个输入队列和消息线程。同一发送者、同一主题的消息保持顺序；不同发送者之间不承诺全局顺序。

背压由订阅者独立承担：

- `Reliable`：队列满时不阻塞调用线程，拒绝新消息，`publish()` 返回 `false`。
- `Latest`：队列满时丢弃最旧消息并保留最新消息，适合图像流。
- 大小超限：在进入队列前拒绝。
- 关闭：停止接受新消息，在 `ShutdownDrainTimeoutMs` 内尽量排空，超时后统计并丢弃剩余消息。

一条消息可能对某些订阅者成功、对另一些订阅者失败，因此模块必须检查 `publish()` 返回值并记录业务上需要的降级行为。

跨进程桥接不会把中央有界队列搬成无上限的 Qt 事件。父进程和子进程各自维护按主题受 `QueueCapacity` 约束的待发送/待处理队列；一次 Qt queued 唤醒只负责合并排空有限批次，不携带完整帧。`Latest` 满时删除同主题仍在等待的最旧帧，`Reliable` 满时拒绝新消息，绝不覆盖旧消息。在途窗口同样按主题受限，因此 Socket 缓冲和共享内存段数量不会随慢消费者无限增长。

## 子进程 IPC

监督器为每次启动生成随机服务器名和令牌，并通过命令行只传给目标子进程。注册帧必须同时匹配模块 ID、模块类型、令牌和主题列表，模块不能只凭 ID 冒充另一个配置项。

数据路径按大小选择：

```text
小消息 -> 有界队列 -> QLocalSocket 帧 -> delivery/publish ACK -> 释放在途槽位
大消息 -> 有界队列 -> QSharedMemory + 控制帧 -> delivery/publish ACK -> 释放共享段和在途槽位
```

父到子的 delivery ACK 在消息进入子进程有界队列后释放父侧槽位；子到父的 publish ACK 在中央 `MessageBus` 接收或拒绝后释放子侧槽位。ACK 拒绝按计数和限频警告记录，不会在高频帧下逐帧刷日志。共享内存只是传输优化。模块 API 始终接收完整 `QByteArray`，不拥有共享内存句柄。正常确认、断开、故障、重启和关闭都会唤醒等待并清理框架持有的队列与共享段。

业务线程调用 `publish()` 时只进入受 `QMutex` 保护的本地 `PublishQueue`，不读取
`ProcessRuntime::running_`，也不查询 `QLocalSocket`。Socket 状态、编码和 write
只在 Runtime 所属 Qt 线程执行，并由线程归属断言保护。控制帧写失败立即进入
transport fault/退出流程；父进程心跳只有写成功才开始等待 pong。

发送队列把生命周期损失分成三类：尚未写入 Socket 即被覆盖或清理是 dropped，
闸门关闭、大小超限或 Reliable 满是 rejected，已经写入但在断线/停止前没有 ACK
是 abandoned。计数按模块限频告警，并在每个进程 generation 结束时汇总一次。

## 监督与重启

子进程按 `Stopped -> StartingProcess -> WaitingRegistration -> WaitingStarted ->
Running` 推进。`startAll()` 只提交启动；全部目标第一次到达 Running 或 Failed 后，
`startupBatchFinished` 才放开 MessageBus 消费。监督器定期发送心跳；注册超时、
心跳超时、启动错误和异常退出都进入故障处理。

停止或重启先在锁内关闭父到子入口，再关闭 MessageBus 单模块入口并清等待项，
随后建立该 Entry 自己的 stop deadline，最后发送 stop。stopAck 会把阶段从
`WaitingStopAck` 推进到 `WaitingProcessExit`；超时只升级该 Entry，不借用或重置
其他模块的 deadline。普通操作没有嵌套 `processEvents()` 或同步进程等待；应用
最终退出才使用一个覆盖全部子进程的总 deadline，并对剩余完整 `QProcess` 执行
`terminate()`/`kill()`。

在 `RestartWindowMs` 窗口内，框架最多自动重启 `MaxRestartCount` 次，每次等待
`RestartDelayMs`。超过上限后停止自动重启、写错误日志并弹窗。用户手动重启只
提交异步请求，会清空计数并重新建立随机令牌、IPC 服务和消息队列；busy 期间
重复请求立即拒绝，最终结果由 `restartFinished` 通知 UI。

Debug 模式的 `WaitForDebugger` 在子进程调用 `onStart()` 前等待附加；Release 模式忽略该选项，防止发布目录因调试配置停住。

## 有界退出与卡死隔离

`onMessage()` 在队列锁外执行。停止超时时，框架可以丢弃并统计尚未进入回调的
消息，却不能安全中断已经进入 DLL 业务代码的线程。主进程模块因此采用
quarantine：保留仍运行的 `QThread`、endpoint 和 plugin loader，跳过并发
`onStop()` 与 DLL 卸载。FrameworkRuntime 继续停止其他安全组件，并只在应用原本
就在退出的边界通过集中封装请求 process-level fail-fast；普通模块重启不会走
这条路径。

子进程模块使用不同的隔离边界。`ProcessRuntime` 不调用 `QThread::terminate()`，
回调超时后也不销毁仍被线程使用的对象，而是让整个子进程结束。父进程在独立
stop deadline 到期后可以对完整 `QProcess` 调用 `terminate()/kill()`；这不会把
一条可能持锁的线程留在原进程中继续运行。

## UI、Dock 与子进程窗口

主窗口在首次启动时保持空白，但 UI 模块可以已经完成 `onStart()`。用户第一次显示模块时，框架把 Dock 放到左侧；多个 Dock 默认可以成为标签页。

模块 Dock 有两类独立状态：`requestedDockVisibility_` 表示用户或布局希望显示，
`uiAvailable_` 表示 QWidget/HWND 已经 ready。只有两者都为 `true` 才实际显示。
QAction 始终反映前者；标签切换只改变 Qt 当前绘制页，不能取消菜单勾选。
`ManagedDockWidget::closeRequested()` 才表示用户按下关闭按钮，此时撤销显示意图，
但不停止模块。

主进程 UI 模块本身是 QWidget，框架把它交给自己的 QDockWidget 管理。子进程 UI 先上报原生 HWND，主进程用 `QWindow::fromWinId()` 建立窗口容器并放入 Dock。`ProcessWindowHost` 忽略外部窗口的历史 size hint，以自己的客户区约束 Dock；连续 resize 由 50 ms 单次 `QTimer` 合并。Dock 拖动、上下拆分或恢复布局时，Qt 可能短暂隐藏宿主，因此定时器只检查嵌入容器是否仍存在，不能用瞬时 `isVisible()` 丢弃最终尺寸。MainWindow 再用稳定的显示意图、window ready 和 `Running` 状态决定是否发送独立 `resizeWindow` 帧。子进程收到该帧只调用 `QWidget::resize()`，不会重复 `show()`。

子进程重启期间 Dock 保留位置，以占位文本显示状态。旧原生容器先隐藏并从布局移除，再由 Qt 事件循环延迟销毁，避免与仍在处理的 HWND resize/paint 事件重叠。若布局希望显示但 HWND 晚到，框架保留 pending；window ready 后自动补显示。布局明确隐藏时不会补显示，隐藏期间的尺寸事件也不能使窗口重新出现。

### 无边框标题栏与 Dock 分隔条（2026-08-05）

主窗口的顶层外壳由 `WindowTitleBar` 提供。它是普通 Qt `QWidget`，通过 QObject 父子
关系拥有 `QMenuBar` 和三个 `QToolButton`，不再创建额外图标或名称 `QLabel`，只发出窗口操作 signal；
`MainWindow` 继续拥有 QAction、Dock、布局和模块生命周期。这样菜单迁移只是更换 QAction
的显示容器，不会复制“加载布局/模块显示/QSS 重载”等业务逻辑。

`Qt::FramelessWindowHint` 移除了 Windows 原生非客户区，所以 `MainWindow::nativeEvent()`
在 Windows 下补回 `WM_NCHITTEST` 的八方向缩放和 `WM_GETMINMAXINFO` 的任务栏工作区
最大化。屏幕物理坐标先转换为 Qt `QPoint`/`QRect`；标题栏保持 `HTCLIENT`，空白区由
`WindowTitleBar` 发出 signal，再调用 Qt `QWindow::startSystemMove()`。这段平台代码不进入
模块或 SDK，非 Windows 平台沿用 Qt 默认事件处理。

Dock 之间的手柄属于 `QMainWindow::separator`，业务 `QSplitter` 的手柄仍由
`QSplitter::handle` 独立控制。`StyleManager` 在 `QApplication` 基础样式上安装
`QProxyStyle`：前者保留约 5px 命中范围，但普通/悬浮状态实际只绘制中央 1px，
不改变 Dock 的 `180 x 120` 最小尺寸、标签关系或 `.qflayout` 格式。

示例模块的日志显示也必须与布局约束隔离：ProcessNonUi 的启动演示会发布较大的
共享内存消息，但 InProcessUi 和 ProcessUi 只显示有界预览，并用 `QSizePolicy::Ignored`
和零最小宽度避免 `QLabel::sizeHint()` 反向撑大 Dock。完整消息仍按原协议解码、计数和
传输；因此重启 ProcessNonUi 不会改变仍在运行的 ProcessUi HWND 客户区。

## 布局与样式为什么彼此独立

`.qflayout` 保存主窗口几何、Qt `saveState()` 数据和模块显示意图。Qt state 负责
Dock 位置、标签关系、尺寸和活动标签；JSON 的 `requestedVisible` 负责用户是否
希望显示，不能再用非当前标签的瞬时 `isVisible()` 代替。新布局同时保留
`visible` 兼容字段并标记 `visibilitySemantics=userIntent`；旧布局仍读取
`visible`，加载后提示用户确认并重新保存。布局完整校验和恢复成功后才替换
当前显示意图，失败则保留原布局和活动文件。它不保存 QSS，只有用户明确保存时
才写文件。

布局预设来自只读 `QFramework.ini` 的连续 `[Layout.n]` 分组。`FrameworkConfig` 在启动时
把 `Name/File` 复制为 Qt 配置快照并解析相对路径；`MainWindow` 创建对应的 `QAction`，用
`QActionGroup` 保持一个当前预设的勾选状态。只有预设加载成功后，`LayoutManager` 才更新
活动文件路径；“加载布局...”和“布局另存为...”使用保持活动路径的调用策略。因此用户可以
在当前选中 `Layout.2` 时查看或加载其他文件，随后“保存当前布局”仍明确覆盖 `Layout.2`。
预设文件的静态校验不会修改窗口，Qt 恢复失败会在原窗口状态上回滚。

`StyleManager` 保存当前 QSS 路径和文本。成功切换后，主进程立即应用并把同一文本通知 `ProcessUi` 子进程；失败时保留上一个成功样式。运行中的选择不写回 INI，因此重新启动仍以 `[Style]/File` 为准。

## 配置与日志的所有权

`FrameworkConfig` 在启动时读取固定的 `config\QFramework.ini`，随后只提供内存快照和路径解析。程序没有保存 INI 的代码路径，这使运维修改可审计，也避免 GUI 操作悄悄改变下次启动行为。

`Logger` 是异步、线程安全的单例。模块日志和 Qt 全局日志最终进入同一按日期与大小滚动的文件。普通记录默认每 100 ms 形成一批并只调用一次 `QFile::flush()`；显式刷新、Fatal、换日、大小滚动和停止仍立即刷新。框架状态故障会同时记录并提示用户；解析失败、队列丢帧等高频业务故障只记录和计数，避免重复弹窗阻塞操作。

## 首版明确不提供的能力

- 同步 RPC 或请求响应框架；
- 运行时订阅、取消订阅；
- 持久消息、离线补发；
- 主进程 DLL 热更新；
- 自动 ABI 兼容检查；
- 安装程序或自动修改 INI；
- 硬性性能通过阈值。

这些边界保持实现简单且可验证。需要新能力时，应先扩展冻结设计和测试，再改变公共 SDK。
