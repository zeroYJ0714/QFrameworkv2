# 教程：创建并配置四类模块

> 文档修订：2026.08.10
>
> 目标读者：第一次把 Qt/C++ 项目接入当前 QFramework 的模块开发者

本教程适合已经会创建普通 Qt/C++ 项目，但第一次接入 QFramework 的开发者。完成后，你会得到一个位于 `Modules\<ModuleId>`、加入唯一 `QFramework.sln`、可在 Win32/x64 和 Debug/Release 下构建的模块。

## 1. 先确定模块类型

| 模块类型 | 项目输出 | 基类 | Qt 组件 | 额外文件 |
| --- | --- | --- | --- | --- |
| `InProcessUi` | DLL | `qframework::InProcessUiModule` | `core;gui;widgets` | 插件 JSON、`Q_PLUGIN_METADATA` |
| `InProcessNonUi` | DLL | `qframework::InProcessNonUiModule` | `core` | 插件 JSON、`Q_PLUGIN_METADATA` |
| `ProcessUi` | EXE | `qframework::ProcessUiModule` | `core;gui;widgets;network` | `QApplication` 入口 |
| `ProcessNonUi` | EXE | `qframework::ProcessNonUiModule` | `core;network` | `QCoreApplication` 入口 |

UI 模块在主窗口中对应一个 Dock；非 UI 模块没有 Dock。只有主进程 DLL 使用 Qt 插件元数据。子进程 EXE 必须由框架启动，不能作为普通独立程序运行。

## 2. 在唯一解决方案中创建项目

1. 用 VS2026 或 VS2017 打开仓库根目录的 `QFramework.sln`。
2. 通过“添加新项目”创建 Qt 默认 DLL 或 EXE 项目。
3. 把项目目录设为 `Modules\<ModuleId>`，并把项目加入当前解决方案。
4. 不创建第二个 `.sln`，不引入 qmake、CMake、自定义模块模板或仓库共享 `.props`。
5. 为项目建立 `Debug|Win32`、`Debug|x64`、`Release|Win32`、`Release|x64` 四个组合。

## 3. 配置常规属性

在“项目属性”中逐一核对四个配置组合：

| 属性 | 值 |
| --- | --- |
| Windows SDK 版本 | `10.0.19041.0` |
| 平台工具集 | `v141` |
| 字符集 | Unicode |
| DLL 模块配置类型 | 动态库 `.dll` |
| 子进程模块配置类型 | 应用程序 `.exe` |

每个项目在 `.vcxproj` 内联定义架构名：

```xml
<QFrameworkArch Condition="'$(Platform)'=='Win32'">x86</QFrameworkArch>
<QFrameworkArch Condition="'$(Platform)'=='x64'">x64</QFrameworkArch>
```

输出目录和中间目录使用：

```text
$(SolutionDir)Bin\v141\$(QFrameworkArch)\$(Configuration)\Plugins\<ModuleId>\
$(SolutionDir)Build\Intermediate\<ModuleId>\$(QFrameworkArch)\$(Configuration)\
```

## 4. 选择匹配架构的 Qt

在 `Qt Project Settings` 中设置：

| 平台 | Qt Installation |
| --- | --- |
| Win32 | `5.15.2_msvc2019` |
| x64 | `5.15.2_msvc2019_64` |

`Qt Modules` 使用第 1 节表格中的值。Qt 包名中的 `msvc2019` 不会改变项目的 `v141` 工具集。当前主进程 DLL 示例的 `Qt Plugin` 属性保持“否”，插件身份由源码中的 `Q_PLUGIN_METADATA` 声明。

## 7. 正确设置 Qt 项目项类型

包含 `Q_OBJECT` 的头文件必须作为 `QtMoc` 项加入项目；普通 `.cpp` 使用 `ClCompile`，插件 JSON 使用 `None`。同一路径不能同时作为 `QtMoc` 和 `ClInclude` 出现，否则 VS2026 会拒绝加载项目。

```xml
<ItemGroup>
  <QtMoc Include="MyModule.h" />
  <ClCompile Include="MyModule.cpp" />
  <None Include="MyModule.json" />
</ItemGroup>
```

## 8. 实现主进程 DLL 模块

主进程 UI 模块：

```cpp
#include "InProcessUiModule.h"
#include "QFrameworkPlugin.h"

class MyUiModule final : public qframework::InProcessUiModule
{
    Q_OBJECT
    Q_PLUGIN_METADATA(IID QFRAMEWORK_PLUGIN_IID FILE "MyUiModule.json")

public:
    explicit MyUiModule(QWidget* parent = nullptr);
};
```

主进程非 UI 模块把基类改为 `qframework::InProcessNonUiModule`，构造参数改为 `QObject*`。两个 DLL 都需要元数据：

```json
{
  "ModuleId": "MyUiModule",
  "ModuleType": "InProcessUi"
}
```

`ModuleId`、`ModuleType`、DLL 文件名和 INI 注册项必须相互一致。

如果主进程 UI 模块包含未保存草稿，可以重写关闭确认接口：

```cpp
#include <QMessageBox>

bool MyUiModule::canClose(qframework::ModuleCloseReason reason)
{
    if (!isWindowModified())
        return true;

    const QString action =
        reason == qframework::ModuleCloseReason::ApplicationExit
            ? QString::fromUtf8(u8"退出应用")
            : QString::fromUtf8(u8"隐藏模块");
    return QMessageBox::question(
               this,
               QString::fromUtf8(u8"未保存内容"),
               QString::fromUtf8(u8"仍有未保存内容，确定要%1吗？").arg(action),
               QMessageBox::Yes | QMessageBox::No,
               QMessageBox::No) == QMessageBox::Yes;
}
```

在类声明中同时添加
`bool canClose(qframework::ModuleCloseReason reason) override;`。回调在主进程 GUI
线程执行。示例选择“放弃或取消”；实际模块如果在这里发起保存，保存失败、用户取消
或有限等待超时都应返回 `false`。当前只有已加载的 `InProcessUi` 会在用户隐藏 Dock
和应用退出前收到该回调，`ProcessUi` 不会收到同步关闭询问。

## 9. 实现子进程 EXE 模块

子进程类分别继承 `ProcessUiModule` 或 `ProcessNonUiModule`，不使用 `Q_PLUGIN_METADATA`。入口保持最小。

UI 子进程：

```cpp
#include <QApplication>
#include "ProcessRuntime.h"
#include "MyProcessUiModule.h"

int main(int argc, char* argv[])
{
    QApplication application(argc, argv);
    return qframework::ProcessRuntime::run(
        &application, new MyProcessUiModule);
}
```

非 UI 子进程使用 `QCoreApplication` 和 `MyProcessNonUiModule`。不要解析或伪造框架传入的 IPC 参数；`ProcessRuntime` 负责令牌、注册、心跳、消息与共享内存。

## 10. 声明主题并手工序列化 Protobuf

新模块使用统一协议头：

```cpp
#include "Generated/master_message.pb.h"
#include "MessageTopics.h"
```

当前 `master_message.proto` 只定义 `MsgType` 和外层 `Msg`。四个仓库示例仍包含
`Generated/status_messages.pb.h` 和 `Generated/log_messages.pb.h`，测试还引用旧
`ImageFrame`；这些是尚待迁移的旧演示代码，不是当前 `Msg` 协议的一部分。本轮已经
重新生成只含 `MsgType/Msg` 的 `master_message.pb.*`，真实完整构建也因此暴露了示例的
未解析外部符号，不能再依赖旧生成产物。

模块在启动前静态声明发布和订阅主题：

```cpp
QStringList MyModule::publishedTopics() const
{
    return QStringList() << QString::fromLatin1(QFRAMEWORK_STATUS);
}

QStringList MyModule::subscribedTopics() const
{
    return QStringList() << QString::fromLatin1(QFRAMEWORK_LOG_DISPLAY);
}
```

框架会先开放当前模块的发布入口，再调用 `onStart()`，所以启动回调可以直接发布
初始化结果。无论使用哪个主题，传给框架的 `QByteArray` 都必须是外层 `Msg` 的序列化
结果，不能直接发送业务字节：

```cpp
bool MyModule::onStart()
{
    const QByteArray businessData("ready");

    qframework::protocols::Msg envelope;
    envelope.set_type(qframework::protocols::Test);
    envelope.set_time(QDateTime::currentMSecsSinceEpoch());
    envelope.set_src(moduleId().toStdString());
    envelope.set_dst("TargetModule");
    envelope.set_str(businessData.constData(), businessData.size());

    std::string outer;
    if (!envelope.SerializeToString(&outer)) {
        logError(QString::fromUtf8(u8"序列化外层 Msg 失败"));
        return false;
    }

    if (!publish(QString::fromLatin1(QFRAMEWORK_STATUS),
                 QByteArray::fromStdString(outer))) {
        logError(QString::fromUtf8(u8"发布启动状态失败"));
        return false;
    }
    return true;
}
```

如果 `onStart()` 返回 `false` 或抛出异常，框架会立即撤销发布权限并把本模块标记
为启动失败；之后的 `publish()` 会返回 `false`。示例需要包含 `<QDateTime>`。

`publish()` 已经会在入口把 `QByteArray` 包装为共享载荷，普通业务继续使用它即可。
当已经得到外层 `Msg` 的序列化结果，且缓冲不再由调用方使用时，也可以显式转移它并
调用 `publishShared()`。把上面 `onStart()` 中最后一次 `publish()` 替换为以下代码，
其中 `outer` 仍是刚刚序列化得到的外层 `Msg`：

```cpp
QByteArray serializedMsg = QByteArray::fromStdString(outer);
const qframework::MessagePayload payload =
    qframework::makeMessagePayload(qMove(serializedMsg));

if (!publishShared(QString::fromLatin1(QFRAMEWORK_STATUS), payload)) {
    logWarning(QString::fromUtf8(u8"外层 Msg 未被消息总线接受"));
    return false;
}
```

同进程订阅队列只复制 `MessagePayload` 智能指针；跨进程仍会在 inline 帧或
`QSharedMemory` 边界复制字节。不要创建空的 `MessagePayload()`；零字节业务消息也
必须由非空 `QByteArray` 构造。

接收方也必须先解析外层 `Msg`，再按模块之间的业务约定解释 `str`：

```cpp
qframework::protocols::Msg envelope;
if (!envelope.ParseFromArray(data.constData(), data.size())) {
    logWarning(QString::fromUtf8(u8"外层 Msg 解析失败"));
    return;
}
if (!envelope.dst().empty() && envelope.dst() != moduleId().toStdString())
    return;

const QByteArray businessData(envelope.str().data(),
                              static_cast<int>(envelope.str().size()));
```

`data` 是 `onMessage()` 收到的原始载荷。`Msg.str` 是二进制，不能先转成 `QString`。
中央总线不会读取 `Msg.dst` 或 `MsgType`，订阅者仍需在业务层核对目标模块并解释
`str`。当前 `MsgType` 只有 `None` 和 `Test`，不要引用已从 schema 删除的 SQL、ADB
或设备类型。

UI 模块的 `onMessage()` 在模块消息线程执行。它只能解析数据并发射信号，界面更新必须通过显式 `Qt::QueuedConnection` 切回 GUI 线程。

## 11. 在 QFramework.ini 注册模块

先把模块 ID 加到 `[Modules]/Names` 的目标位置，再添加对应分组：

```ini
[Module.MyUiModule]
Enabled=true
Type=InProcessUi
DisplayName=我的界面模块
FilePath=../Plugins/MyUiModule/MyUiModule.dll
WaitForDebugger=false
DebuggerWaitTimeoutMs=30000
```

四类 `Type` 值必须使用 `InProcessUi`、`InProcessNonUi`、`ProcessUi`、`ProcessNonUi` 之一。相对路径从运行目录中的 `config` 目录解析。程序不会替你修改此文件。

如果模块发布帧流或大消息，还要核对对应 `[Topic.<TopicName>]`。当前
`MessageTopics.h` 只保留 `QFRAMEWORK_IMAGE_RAW`、`QFRAMEWORK_IMAGE_PROCESSED`、
`QFRAMEWORK_LOG_DISPLAY` 和 `QFRAMEWORK_STATUS`；仓库 INI 只把
`QFRAMEWORK_IMAGE_RAW` 配成 `Latest`，其余主题继承全局规则。

## 12. 第一次构建与运行

1. 先生成 `QFrameworkProtocols` 和 `QFramework`，再生成新模块与 `QFrameworkApp`；项目引用通常会自动保证顺序。
2. 对当前配置执行“重新生成解决方案”，确认输出为 0 个失败项目。
3. 手工把仓库的 `config` 目录复制到对应 `Bin\v141\<架构>\<配置>` 目录。
4. 确认模块文件位于 `Plugins\<ModuleId>`，并存在匹配架构和配置的 Qt、QFramework、QFrameworkProtocols 与 Protobuf DLL。
5. 启动 `QFrameworkApp.exe`。UI 模块默认隐藏，通过标题栏左侧“模块”菜单显示。

当前仓库在 2026-08-10 的 `Debug|x64` 验证中，协议 DLL、框架 DLL 和主程序已成功
生成，但四个旧示例仍因 `ModuleStatus/LogDisplayMessage` 未解析而链接失败。因此上面
“0 个失败项目”是接入完成后的验收目标，不是当前工作区已经达到的结果。迁移示例到
`Msg` 或明确拆分演示协议之前，不要把完整解决方案和 Qt Test 记为通过。

## 13. 当前主窗口外观和 Dock 操作（2026-08-10）

主窗口采用 Qt `WindowTitleBar` 绘制的无边框标题栏。现有“布局、模块、样式”菜单位于
左侧，不额外显示图标或 `QFramework` 文字；最小化、最大化/还原、关闭按钮位于右侧；这些按钮只是发出 Qt signal，
不会改变模块 QAction 或布局文件的语义。Windows 下标题栏空白处用于拖动，边缘和四角
用于缩放，窗口最大化使用显示器工作区以避开任务栏。

用户从“模块”菜单取消勾选或点击 Dock 关闭按钮时，主进程 UI 模块可以通过
`canClose(Hide)` 取消本次隐藏；菜单勾选和 Dock 会保持原状态。点击标题栏关闭按钮、
按 `Alt+F4` 或调用主窗口 `close()` 时，会按配置顺序调用已加载主进程 UI 模块的
`canClose(ApplicationExit)`，任一拒绝就取消本次退出。隐藏 Dock 仍不调用
`onStop()`，同意退出后才进入原有框架停止顺序。

两个 Dock 左右或上下停靠时，中间调整手柄由 `QMainWindow::separator` 管理。主题下保留
约 5px 的鼠标命中范围，但实际只显示中央 1px，鼠标悬浮时该 1px 线会高亮。Dock 仍受
现有最小尺寸和布局保存规则限制；如果只能缩小到
`180 x 120`，这是保护模块内容的正常下限，不是菜单或布局故障。

`ProcessUi` 放到上方或下方时，`ProcessWindowHost` 会用 Qt 的 50 ms 单次 `QTimer` 合并
重排产生的 resize，并把最终客户区尺寸交给子进程。Qt 重排期间短暂隐藏 Dock 不代表用户
关闭模块；只有菜单/布局明确要求隐藏时才停止转发。正常结果是停靠完成后立即可以拖动
分隔条，子进程界面也立即铺满，不需要额外缩放主窗口。

### 配置布局预设

模块教程不需要新增布局接口。运行配置可以在 `config/QFramework.ini` 中声明连续的
`[Layout.1]`、`[Layout.2]` 等预设：

```ini
[Layout.1]
Name=默认布局
File=Layouts/Default.qflayout
```

相对 `File` 路径以 `config` 目录为基准，修改后重启程序。框架会在左上角“布局”菜单中
直接显示 `Name`，启动时尝试加载 `Layout.1`；模块只需保持 Dock 的稳定 objectName，
不应自己读取 INI、保存 `.qflayout` 或改变当前预设选择。

## VS2017 差异

VS2017 的属性页布局和 Qt Visual Studio Tools 菜单名称可能与截图不同，但项目值完全相同：仍使用 `v141`、C++17、Qt 5.15.2、对应架构的 Protobuf 库和同一输出目录。不要在 VS2017 中升级工具集，也不要让 VS2026把项目重定向到更高工具集。
